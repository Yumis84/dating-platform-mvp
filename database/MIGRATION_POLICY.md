# Migration Policy — Dating Platform MVP

Дата: 2026-08-07

Цель
----
Фиксирует политику применения миграций в репозитории и даёт инструкции, как безопасно применять их в dev/stage/production окружениях.

Этот документ — **политика применения** (как и когда запускать миграции).  
Он **не** заменяет migration manifest.

- **Порядок файлов (канон):** `docs/MIGRATION_MANIFEST.md` (PR #2)  
- **Политика / safety:** этот файл — `database/MIGRATION_POLICY.md`

Ключевые правила
----------------
1. Никогда не применять миграции простым перечислением файлов в каталоге (например, алфавитной сортировкой) — используйте канонический порядок из `docs/MIGRATION_MANIFEST.md` или запускайте migrator против специально подготовленной директории с нужным подмножеством файлов.
2. Все изменения в файлах миграций требуют PR с описанием причины, тест-плана и SHA прежней версии файла (если файл изменяется).
3. Не менять номера уже опубликованных миграций (001..n) без согласования — это ломает последовательность в средах, где миграции уже применялись.

Canonical first migration
-------------------------
- Выбрана canonical версия первой миграции: `001_users_and_telegram_accounts_schema.sql`.
- Причины выбора:
  - Модель хранения Telegram ID в `telegram_accounts` (отдельная таблица) соответствует архитектурной политике проекта: Telegram ID — контактное поле, не должно дублироваться по другим таблицам (AI_CONTEXT.md, FINAL_HANDOVER.md).
  - Эта версия обеспечивает явную связь `telegram_accounts.user_id → users.id` с ON DELETE CASCADE и помечена в документации как предпочтительная.
  - Наличие Telegram ID непосредственно в `users` (как в альтернативной `001_initial_users_schema.sql`) противоречит принципу разделения PII и усложняет развитие (несколько мест хранения ID).

Почему `001_initial_users_schema.sql` конфликтует
------------------------------------------------
- `001_initial_users_schema.sql`:
  - Создаёт `users` с колонкой `telegram_id` (BIGINT UNIQUE NOT NULL) и другие PII-поля (username, first_name, last_name).
  - Также содержит `audit_events` и иную структуру `telegram_accounts` (варианты полей и constraints отличаются).
- Проблемы:
  - Дублирование ключевого поля `telegram_id` (в `users` и в `telegram_accounts`) приводит к рассинхронизации данных, проблемам целостности и нарушению политики минимизации PII.
  - Наборы CHECK / значения ролей и имена колонок отличаются от выбранного канонического набора (несоответствие констант и constraints).
  - Если обе миграции присутствуют в наборе и применяются по порядку/автоматически, итоговая схема может быть некорректной или непредсказуемой.

План безопасного разрешения конфликта (пошагово)
-----------------------------------------------
Цель: привести репозиторий к единому каноническому набору миграций, не теряя данных и не ломая рабочие среды.

Шаг 0 — Принятие решения (архитектор / владелец проекта)
- Официально утвердите `001_users_and_telegram_accounts_schema.sql` как canonical 001. Задокументируйте решение в `docs/MIGRATION_MANIFEST.md` и в PROJECT_STATUS.md.

Шаг 1 — Канонический порядок и политика (документация)
- **Migration manifest** (порядок файлов, legacy 001, audit gap): поддерживается отдельно в `docs/MIGRATION_MANIFEST.md` (PR #2).
- **Migration policy** (этот файл): правила безопасного применения, бэкапы, reconciliation.
- Не применяйте миграции «вслепую» по всему каталогу `database/migrations/`.

Шаг 2 — Подготовка репозитория для применения миграций (оперативный)
Варианты операций (выберите практику, удобную вам и вашей командой):

Вариант A — Изолированное применение (рекомендовано для быстрого тестирования)
1. Создайте временную директорию (например `migrations_apply/`) и скопируйте туда только файлы, перечисленные в `docs/MIGRATION_MANIFEST.md` в указанном порядке (001_users_and_telegram_accounts_schema.sql, 002..., ... 007...).
2. Запустите migrator (или psql по очереди) из этой директории, применив файлы последовательностью из манифеста.
3. Тестируйте поведение приложений и n8n workflows на чистой базе.

Вариант B — Операция над конфликтным файлом в репозитории (только после согласования)
1. Переименовать конфликтный файл (локально/в VCS) в нечисловой/несортируемый суффикс, например:
   - `001_initial_users_schema.sql` → `legacy/001_initial_users_schema.legacy.sql` или `001_initial_users_schema_conflict.sql`
   (НЕ делайте этого без согласования; в данном документе описано как опция операции)
2. Зафиксировать (commit) переименование и обновить `docs/MIGRATION_MANIFEST.md`.
3. При необходимости сохранить копию старого файла в архивной папке `database/migrations/legacy/`.

Вариант C — Объединение (если нужно сохранить данные/логику из обеих)
1. Написать новую согласующую миграцию `008_reconcile_users_and_audit.sql`, которая:
   - Переводит данные telegram_id из `users` → `telegram_accounts` (только если telegram_accounts не содержит соответствующих записей).
   - Создаёт или корректно расширяет таблицу `audit_events` (с `user_id REFERENCES users(id) ON DELETE SET NULL`, индексом на `user_id`, и дополнительными колонками: `source`, `workflow_id`, `session_id`).
   - Не удаляет legacy-колонки в users — вместо этого переименует их в `telegram_id_legacy` (удаление оставляется на миграцию 009 после валидации).
2. Применить `001_users_and_telegram_accounts_schema.sql` (каноническая), потом 002..007, затем 008 для reconciliation.
3. После успешных smoke tests и подтверждения нормализации данных — создать миграцию `009_remove_legacy_telegram_id.sql`, которая удаляет/архивирует `users.telegram_id` (или выполняет безопасное DROP COLUMN).

Примечание о внесении изменений в репозитории
- Любые переименования/удаления файлов миграций — это изменение истории и должно быть согласовано и зафиксировано через pull request с описанием причин и SHA затронутых файлов.

Audit_events — отдельный раздел
------------------------------
Audit_events — критичный инфраструктурный элемент: WF_01..WF_03 и другие рабочие процессы записывают события в эту таблицу. Требования к audit_events:

Рекомендуемая структура (пример)
```sql
CREATE TABLE audit_events (
  id UUID PRIMARY KEY DEFAULT uuid_generate_v4(),
  user_id UUID REFERENCES users(id) ON DELETE SET NULL,
  event_type TEXT NOT NULL,
  event_data JSONB,
  source TEXT,         -- optional: 'telegram','webapp','system'
  workflow_id TEXT,    -- optional: n8n workflow id that emitted event
  session_id UUID,     -- optional: profile_ai_sessions.id or other session reference
  processed_by TEXT,   -- who handled it (admin id or 'system')
  created_at TIMESTAMP WITH TIME ZONE DEFAULT now()
);

CREATE INDEX idx_audit_events_user_id ON audit_events(user_id);
```

Проверки и подготовка перед применением FK
- Перед добавлением FK `audit_events.user_id → users(id)` убедитесь, что нет orphan записей:
```sql
SELECT count(*) FROM audit_events ae
WHERE ae.user_id IS NOT NULL
  AND NOT EXISTS (SELECT 1 FROM users u WHERE u.id = ae.user_id);
```
- Если `count > 0` — подготовьте процедуру исправления (редирект, удаление, или set user_id=NULL) до добавления FK.

Рекомендации по индексации
- Индекс на `audit_events(user_id)` значительно ускоряет lookups и связку событий с пользователем.
- Дополнительно: индекс по `(event_type, created_at)` полезен для аналитики и поиска по типу события.

Политика безопасности и осторожности
------------------------------------
- Всегда делать полный бэкап базы перед применением миграций в staging/production:
  - pg_dump / pg_basebackup
- Тестируйте миграции на clean clone (dev/stage) перед production.
- Не менять порядок в манифесте без согласования владельца проекта.
- После изменений в миграциях обновляйте `docs/MIGRATION_MANIFEST.md` и публикуйте PR, где указаны SHA изменённых файлов.

Резюме / контрольный чеклист (быстро)
------------------------------------
1. Архитектор утверждает `001_users_and_telegram_accounts_schema.sql` как canonical.
2. Использовать `docs/MIGRATION_MANIFEST.md` + этот policy для детерминированного применения.
3. На clean clone:
   - Убедиться, что `uuid-ossp` доступен.
   - Применить 001..007 (по манифесту).
   - Выполнить reconciliation (008) если нужно переносить данные или сохранять legacy столбцы.
   - Проверить отсутствие orphan audit_events, дубликатов telegram_id.
4. После валидации и smoke tests подтвердить план удаления legacy-колонки в 009.
5. Обновить документацию и CI для применения canonical миграций автоматически в staging.

Контакты и ответственность
-------------------------
- Любое изменение порядка миграций или решений по полям PII должно быть утверждено владельцем проекта (архитектор). Запросите подтверждение перед изменением файлов `database/migrations/*`.
